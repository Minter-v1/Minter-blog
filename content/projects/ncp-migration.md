## 개요

클라우드스퀘어 클라우드 2팀 현장실습에서 받은 가상 고객사 시나리오입니다. 제조기업이 온프레미스 서버 한 대로 운영하던 인사관리시스템을 NCP로 옮기는 과제였고, 요구사항 분석부터 설계, 구축, 이전 검증까지 1인으로 전 과정을 맡았습니다.

## 배경

고객사의 인사관리시스템은 WEB, WAS, DB가 모두 한 서버에 올라가 있었습니다. 서버 한 대가 멈추면 OS와 애플리케이션을 다시 띄울 때까지 30분 넘게 전체 서비스가 중단됐고, 요청이 몰리는 월말에는 서버를 손으로 늘려 버텨야 했습니다.

과제 조건도 분명했습니다. 이전은 허용 중단 4시간 안에 끝내야 했고, 문제가 생기면 다시 온프레미스로 돌아갈 수 있어야 했습니다. 고객사 요구사항 19개를 인프라 조건으로 하나씩 옮겨 적은 뒤, 서버 장애와 월말 부하를 사람 손 없이 흡수하는 것, 그리고 65GB를 정합성 손실 없이 옮기고 되돌릴 수 있는 것을 목표로 잡았습니다.

## 아키텍처

WEB, WAS, DB를 나누고 KR-1, KR-2 두 존에 이중화했습니다. 서버가 죽으면 Auto Scaling Group이 새 서버로 교체하고, 교체되는 동안에는 다른 존이 요청을 받습니다. 부하에 따라 늘어나는 건 WAS만 2대에서 4대까지로 잡았습니다.

[![NCP Multi Zone 3-Tier 아키텍처 (클릭하면 원본)](/projects/ncp-migration/architecture.png)](/projects/ncp-migration/architecture.png)

DB는 MySQL Primary와 Standby로 HA를 구성하고 조회용 Read Replica를 따로 두었습니다. 서버 접속은 Bastion Host로만 열고, 서브넷과 NACL, ACG로 계층마다 접근을 막았습니다.

## Auto Scaling이 엉뚱한 서버를 교체하던 문제

Auto Scaling을 붙이고 나서 가장 오래 붙잡은 부분은 "언제 서버를 교체할지"였습니다.

처음에는 Spring Boot의 `/actuator/health`를 헬스체크로 썼는데, 이 엔드포인트는 DB 상태까지 포함합니다. 그래서 DB가 잠깐 끊기면 멀쩡한 WAS까지 503으로 판정돼 계속 교체됐습니다. WAS 자체가 살아 있는지만 보는 `/actuator/health/liveness`로 바꾸고, DB 장애는 교체 대신 Cloud Insight 알림으로 받도록 분리했습니다.

WEB 쪽은 반대 문제가 있었습니다. Nginx가 `/health`에 항상 200을 돌려주고 있어서, 뒤의 Next.js가 멈춰도 서버는 정상으로 보였고 사용자만 502를 받았습니다. `/health`를 Next.js까지 프록시해서 실제 사용자 요청과 같은 경로로 판정하게 바꿨고, 이후에는 Next.js가 죽으면 Target이 DOWN으로 바뀌어 WEB 서버가 자동 교체됐습니다.

결과적으로 장애가 나면 먼저 Docker Restart Policy로 컨테이너를 재시작하고, 그래도 헬스체크에 실패할 때만 VM을 교체하는 흐름이 됐습니다.

## 새로 뜬 서버가 기동하지 못하던 문제

Auto Scaling으로 새로 늘어난 VM이 헬스체크에 실패해 교체를 반복했습니다. 추적해 보니 VM 자체는 정상이었고, 서버에 Server Role이 연결되지 않아 컨테이너가 Secret Manager에서 DB 접속 정보를 받지 못하고 있었습니다.

권한 상태를 1분마다 조회하면 변화가 없어도 하루 최대 1,440번을 호출하게 됩니다. 그래서 상태가 바뀌는 시점에만 실행하는 방식을 택했습니다. 서버가 RUN 상태가 되면 Observer가 감지하고, Cloud Function이 Role을 연결한 뒤 Secret 조회, 애플리케이션 기동, 헬스체크가 차례로 이어지도록 묶었습니다.

적용 후 신규 서버는 교체 없이 서비스에 합류했고, 증설이나 교체로 생긴 서버에 손으로 작업할 일도, 서버에 Access Key를 둘 일도 없어졌습니다. 이때부터 자동화가 끝났다고 보는 기준을 "리소스가 생성됐다"가 아니라 "서비스가 정상 동작한다"로 두고 있습니다.

## 65GB 이전과 롤백 검증

이전 대상은 DB 25GB와 첨부파일 40GB였고, 고객사가 허용한 중단 시간은 4시간이었습니다. 사용자가 없는 토요일 22시부터 일요일 01시까지 3시간 작업 창을 잡았습니다.

DB는 mysqldump를 포함해 다섯 가지 방법을 비교한 뒤 DMS로 초기 적재와 Replication을 진행했고, 49분 만에 12,800행, 25GB가 일치하는 것을 확인했습니다. 첨부파일은 s3cmd로 Full Sync를 먼저 돌리고(7분), 같은 sync를 다시 실행해 변경분만 맞췄습니다. 파일 52개는 SHA-256으로 비교했습니다.

| 단계 | 소요 | 내용 |
| --- | --- | --- |
| DB 이전 | 70분 | 쓰기 차단 후 DMS 이전, 정합성 검증 |
| 파일 이전 | 60분 | Replication 종료, 첨부파일 Full·Delta Sync |
| Cutover | 20분 | NCP로 트래픽 전환, DB·파일 연결 확인 |
| Go-Live | | DNS·응답 확인 후 쓰기 차단 해제 |

이전만큼 신경 쓴 건 되돌아가는 길이었습니다. NCP 쪽 쓰기를 막고 Binlog Checkpoint부터 온프레미스로 역방향 복제를 걸었고, 첨부파일은 Reverse Sync로 돌려보냈습니다. DB는 CRC32와 행 수, 파일은 SHA-256으로 확인했고 불일치는 없었습니다. 롤백 전체 소요는 60분으로 계획했습니다.

## 하지 못한 것

과제 기간 안에 월말 트래픽을 재현한 부하 테스트는 하지 못했습니다. WAS가 4대까지 늘어나는 데 걸리는 시간과 그때의 응답 시간은 아직 측정값이 없습니다. 롤백도 단계별로는 검증했지만 쓰기 차단부터 DNS 원복까지 한 번에 이어서 실측하지는 않았고, 알림은 CPU 경보만 실제 수신을 확인했습니다. 실제 운영이라면 이 세 가지를 먼저 채웠을 것입니다.
