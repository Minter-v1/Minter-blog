# 프로젝트 상세 문서 표준

## 1. 역할 분리

| 구분 | 독자 | 역할 |
| --- | --- | --- |
| 카드 (`lib/profile.ts`) | HR | 30초 안에 무엇을, 어떤 역할로, 어떤 결과를 냈는지 |
| 상세 본문 (`content/projects/{slug}.md`) | 기술 면접관, 작성자 | 설계 근거, 구현, 트러블슈팅, 검증 |
| PDF (`/about/portfolio`) | HR, 1차 검토 | 주력 프로젝트 빠른 파악 |
| 관련 학습 기록 (`related`) | 작성자, 면접관 | 개념 학습·회고는 블로그 글로 분리하고 상세 하단에 연결 |

한계·회고 섹션은 두지 않는다. 회고와 개념 학습은 블로그 글로 쓰고 `related`로 연결한다.

## 2. 템플릿

상세 페이지 상단의 기간·이름·팀·역할·요약·스택·저장소는 `lib/profile.ts`에서 렌더링하므로 본문에 다시 쓰지 않는다.

```md
> 프로젝트의 목적과 핵심 구현을 설명하는 한 문장

## 프로젝트 요약

| 항목 | 내용 |
| --- | --- |
| 소속 | 어디서 수행했는지 |
| 기간 | |
| 형태 | 팀 규모와 구성 |
| 역할 | |
| 담당 범위 | 직접 수행한 범위 |

### 핵심 성과
- 측정 근거가 있는 성과 2~4개

### 주요 기여
- 직접 수행한 작업. 팀 성과와 구분

## 1. 프로젝트 개요
### 1.1 배경
### 1.2 문제 정의      (기존 상태 → 문제 → 해결 필요성)
### 1.3 목표와 요구사항
### 1.4 제약 조건      (필요할 때만)

## 2. 시스템 설계
### 2.1 전체 아키텍처  (다이어그램 + 설계 의도)
### 2.2 설계 의사결정  (문제 · 선택 · 근거 · 검토한 대안)
### 2.3 기술 스택      (분류 | 기술 | 사용 목적)

## 3. 주요 구현
### 3.1 [구현 단위]    (목적 · 동작 원리 · 구현 · 결과)

## 4. 트러블슈팅
### 4.1 [문제를 구체적으로 표현한 제목]
**현상** / **원인 분석** / **해결** / **검증**

## 5. 검증 및 성과
### 5.1 검증 방법
### 5.2 결과

## 참고자료              (공개 가능한 링크가 있을 때만)
```

- 섹션 번호와 이름은 모든 문서에서 같게 쓴다. 해당 내용이 없는 섹션은 통째로 빼고, 남은 섹션의 번호는 바꾸지 않는다. (예: 트러블슈팅이 없으면 3 다음이 5)
- 분량은 프로젝트 성격에 맞춘다. 같은 분량을 강제하지 않는다.

## 3. 문체와 표기

- 설명 문장은 "-다." 체로 쓴다. ("~했습니다", "~해요" 금지)
- 개조식은 프로젝트 요약, 핵심 성과, 주요 기여, 요구사항, 기능 목록, 비교 항목에만 쓰고 명사형으로 끝낸다.
- 문제 정의, 설계 근거, 구현 원리, 트러블슈팅, 검증 해석은 설명체로 쓴다. 원인과 결과를 한 문장 안에서 잇는다.
- 한 문장에 한 메시지. 수식어를 줄이고 구체적인 수치·설정값을 쓴다.
- "최적화, 고도화, 안정성 확보, 무중단, 완전 자동화, 성능 개선, 비용 절감"은 근거가 본문에 있을 때만 쓴다.
- 계획만 한 값은 "계획"으로, 목표치는 "목표"로 표기한다. 측정값과 섞지 않는다.
- 표기: 기술명은 공식 표기(GitHub Actions, Auto Scaling, Cloud DB for MySQL), 단위는 숫자와 붙여 쓴다(20.7초, 65GB).

## 4. 블록 사용 기준

이 사이트의 상세 본문은 GFM 마크다운이다. 지원: 표, 이미지, 코드 블록(하이라이트), Mermaid, 인용문, 접기(`<details>`).

| 블록 | 쓰는 곳 | 쓰지 않는 곳 |
| --- | --- | --- |
| 인용문 `>` | 문서 첫 줄 한 문장 요약, 공개 범위 안내 | 일반 강조 |
| 표 | 프로젝트 요약, 요구사항, 대안 비교, 트러블슈팅이 아닌 Before/After | 3열 초과 (모바일 가로 스크롤) |
| 이미지 | 아키텍처, 화면, 측정 결과 | 글자가 작은 발표 슬라이드 통째 사용 (불가피하면 클릭 시 원본) |
| 코드 블록 | 핵심 설정·스크립트 일부 (10~20줄) | 전체 소스 |
| Mermaid | 흐름(배포, 장애 전환, 복구) | 정적인 구성도 (이미지 사용) |
| 접기 | 긴 설정, 상세 수치 표 | 핵심 성과, 개인 기여 |

## 6. 체크리스트

- [ ] 첫 줄 한 문장 요약이 있다
- [ ] 프로젝트 요약 표에 소속·기간·형태·역할·담당 범위가 있다
- [ ] 핵심 성과의 수치마다 측정 근거가 본문에 있다
- [ ] 개인 기여와 팀 성과가 구분된다
- [ ] 설계 의사결정마다 선택 근거가 있다. 검토하지 않은 대안을 쓰지 않았다
- [ ] 기술 스택에 사용 목적이 있다. 본문에 없는 기술이 스택에 없다
- [ ] 트러블슈팅마다 현상·원인 분석·해결·검증이 있다. 실제로 겪은 문제만 썼다
- [ ] 설명 문장이 모두 "-다." 체다
- [ ] 비밀번호·키·개인정보·대외비 내용이 없다
- [ ] 3열 초과 표가 없거나 모바일에서 읽힌다
